## 1. Outcome

A user describes one tattoo and its location in the ordinary
**Refine this person** prompt. Drape:

1. recognizes an `ink.add` request;
2. resolves a closed anatomical tuple on the server;
3. chooses the strongest current source view;
4. shows the resolved request and exact 350-credit candidate price before
   generation;
5. creates one private 1K candidate with an included internal retry;
6. exposes Accept / Retry / Cancel;
7. on Accept, appends one typed tattoo feature and selects the accepted view;
8. identifies only the package views that can show that tattoo;
9. never refreshes, generates, accepts, or spends automatically; and
10. preserves every earlier accepted tattoo predicted visible in the target
    view.

The public product has no chest selector, anatomy form, recipe names, or
technical package controls. Optional pointing may help Drape resolve a
location, but natural language is sufficient and the server remains the
authority.

R7-7G completes **tattoo addition**. It does not add removal, replacement,
cover-up, movement, resizing, or recolouring of accepted tattoos. It does not
enable cybernetics, moles, scars, freckles, or other permanent-feature
families.

## 2. Founder contracts preserved

- Casting generation and identity-pack export are 1K-only in this release.
- Candidate generation costs 350 credits. One internal retry is included.
- A retry requested by the user is a new priced candidate episode.
- A package-view generation costs the existing canonical slot price.
- Every price is displayed before the action that can charge it.
- Authorization, unsupported anatomy, insufficient coverage, ambiguity,
  provider failure before durable delivery, and failed/unknown evidence probes
  fail closed.
- Failed paid delivery is refunded exactly once through the durable operation
  receipt.
- Accept and Cancel are free.
- Private reference plates, candidates, and evidence crops retain the R7-7D
  private-storage and owner-delivery boundaries.
- No provider call or credit spend occurs from typing, hover, opening history,
  opening package health, accepting a previous state, or changing views.
- Whole-Cast history and restore remain append-only and must carry every
  selected tattoo feature.
- Mint and fork consume the same typed feature graph; no client prompt becomes
  identity authority.

## 3. Product interaction

### 3.1 Normal entry

The existing prompt is the only public authoring entry:

> Add a black botanical full sleeve to her right arm.

The client may use a small tattoo vocabulary only to choose which protected
server door to try. It is not allowed to decide operation, anatomy, source
view, visibility, staleness, or price. The ordinary iteration route keeps its
permanent-mark refusal, so a missed or manipulated client classification
cannot bypass the evidence door.

### 3.2 Free server plan

Submitting tattoo language first creates a free, durable intent plan. The
server returns only public product truth:

- normalized user instruction;
- a human location label, for example `Right arm · full sleeve`;
- the chosen source-view label;
- whether that current view has enough coverage;
- optional reference status;
- candidate price; and
- a static refusal or a ready-to-generate state.

Private ontology keys, row IDs, storage keys, probe recipes, feature text from
other tattoos, and evidence locations never enter the public DTO.

If the instruction is ambiguous, contradictory, contains multiple separate
tattoos, requests a different operation, or resolves to no calibrated tuple,
the request refuses free with a useful correction. Drape never guesses.

### 3.3 Explicit generation and review

After the free plan, the prompt area becomes a compact confirmation:

- the original instruction;
- Drape's human-readable resolved location;
- an optional reference-image attachment;
- `Generate preview · 350 credits`; and
- Cancel.

There are no anatomy buttons. The generated candidate temporarily replaces the
active source image in the viewer. The existing comparison and
Accept / Retry / Cancel lifecycle remains.

After acceptance, Package Health shows only contextual actions such as:

> Preview Back to carry the right-arm sleeve · 300 credits

The UI does not say “sync ontology”, “select surface”, or “manage reference
sheet”.

unrepresented regions are outside the release registry and refuse free.

One request adds one anatomically contiguous feature. “A sleeve on each arm”
is two tattoos and is refused with guidance to add one arm at a time. A full
sleeve on one arm is one `full_arm + circumferential` feature.

### 4.3 Source-view choice

The server registry owns an ordered source preference for every tuple:

- face/scalp/neck prefer the close view that exposes the requested surface;
- anterior torso, anterior limbs, hands, hips, and feet prefer Front;
- lateral surfaces prefer Walk or 3/4 when the requested body part is
  sufficiently visible;
- posterior surfaces prefer Back;
- circumferential sleeves choose the strongest current view for initial
  authoring but do not pretend that one image proves the hidden circumference.

The chosen source must be selected in the current package, compatible with the
current identity, unpinned, and pass a free visibility/coverage probe. If no
current source is sufficient, Drape refuses free and recommends one deliberate
coverage action. It never generates that prerequisite implicitly.

For face/scalp/neck tuples authored on the identity anchor, acceptance creates
a new anchor-bearing identity snapshot. Other tuples preserve the existing
headshot anchor. In both cases the feature graph and package snapshot advance
atomically.

## 5. Visibility and first-unseen-region law

The v2 registry is exhaustive over:

`feature tuple × canonical target angle`.

Each entry declares:

- existing-selection impact: `affected | unaffected | uncertain`;
- visibility: `authoring_truth | reproduce_visible | hidden_omit |
  outside_frame_omit | below_resolution_omit | conditional_probe`;
- normalized target geometry when visible;
- required anatomical side and allowed camera direction;
- whether the current accepted plates prove the visible surface;
- whether a missing/current target may compose; and
- whether Accept / Retry / Cancel is required.

Rules:

1. `unaffected` views remain current and never offer a paid preservation
   refresh.
2. `uncertain` requires a free observed-coverage check and refuses free if
   that proof remains unknown. It is not treated as affected merely to sell a
   refresh.
3. `hidden_omit` and `outside_frame_omit` must prove that the new tattoo was
   not invented in the image.
4. `below_resolution_omit` records that the physical region exists in the
   image but cannot carry reproducible tattoo detail at the release's 1K
   resolution. It is distinct from hidden anatomy and is probe-enforced.
5. A previously accepted target containing the visible tattoo pixels may be
   refreshed through the ordinary explicit package action.
6. A view that would reveal tattoo surface not already present in an accepted
   authoring/projection plate must become a **private projection candidate**
   with Accept / Retry / Cancel. A paid click is not itself acceptance of
   unseen visual evidence.
7. Accepting a projection candidate appends package and evidence rows but does
   not create a second logical tattoo feature.
8. A full sleeve is therefore valid without pretending the hidden side is
   fixed by its first Front candidate. Walk and Back can each earn accepted
   surface evidence as the user deliberately expands coverage.

## 6. Multiple-tattoo graph

The current one-feature guards are removed only after positive multi-feature
closure exists.

For an identity snapshot with `N` selections:

- there are exactly `N` distinct selected feature IDs;
- there are exactly `N` distinct selected version IDs;
- every selection joins to one owned ink feature and one owned version;
- every version joins to its accepted authoring plate;
- every optional projection plate joins through an explicit feature/version
  evidence relation;
- every recipe, ontology, source angle, source asset, storage key, MIME, hash,
  size, and ownership proof closes;
- duplicates, missing rows, foreign rows, unknown recipe versions, or
  unsupported tuples fail the entire graph closed.

Accepting a new tattoo uses the existing transition shape:

- carry every current selection unchanged;
- append one feature, one version, and one accepted selection;
- select the accepted candidate asset for its source angle;
- mark only registry-affected selections stale;
- leave registry-unaffected selections current.

Later tattoos use the complete current target image, which already contains
the earlier visible tattoos. Candidate probes compare the original target with
the candidate and require:

- the new feature at the resolved tuple;
- every prior tattoo predicted visible to remain;
- no earlier tattoo to move, resize, disappear, recolour, mirror, or duplicate;
- no unauthorized new ink; and
- identity, body, pose, framing, clothing, lighting, and background
  preservation under the existing edit contract.

Package composition receives the current target plus a private in-memory
evidence mosaic containing only the selected features predicted visible in
that target. The mosaic is generated from verified private accepted crops,
never persisted as a public product derivative, and never exported. If the
relevant evidence cannot be represented legibly within the bounded composer
input, composition refuses free rather than dropping a feature.
