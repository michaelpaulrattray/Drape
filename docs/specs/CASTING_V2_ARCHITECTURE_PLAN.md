## Context

Drape's current Casting Studio works, but it reads as an expert cockpit: a 31-field identity form, five Zustand stores, three session modes, eight-plus confirmation dialogs, and ~14,700 lines of client casting/studio code wired together by 21 window CustomEvents. The founder's first-time-user walk (FABLE_R7_CASTING_STUDIO_UX_REVIEW.md) found the primary action undiscoverable and the whole surface "an expert control panel rather than a calm creative tool." A design handoff (drape-foundation package + Klieg Casting prototype) settles a new product shape — *sentence → streaming sheet of eight → Keep/Discard/Follow → Sign one → Casting Room* — plus a shared app foundation (tokens, 76px rail, 56px topbar, light/dark themes). Separately, the experimental tattoo/computer-vision projection stack was reverted at `ffc1e0d` (7,280 deletions), and the provider strategy is now settled as two engines: **GPT Image 2** for creative candidate rolls and **Nano Banana Pro** for identity-preserving work, behind a server-owned provider boundary.

This plan is the authoritative reconciliation of: the design handoff, the planning brief, the current repository at `ffc1e0d`, verified provider capabilities, and the surviving R7 backend foundations. It answers the architecture prompt's required sections A–O.

## A. Executive judgment

**Does the supplied foundation fit Drape?** Yes — and it fixes real, verified defects. The current client runs *three* parallel token systems (`styles/tokens.css` marketing tokens, the shadcn oklch palette in `index.css`, and `styles/canvas-tokens.css`), a ThemeProvider whose persistence is dead code (`switchable` defaults false, so `localStorage["theme"]` is never read; there is no first-paint script, so first paint is unthemed), and a 216px text rail (`LobbyRail.tsx`) that the handoff's 76px rail supersedes. The foundation's 38-token dual-theme system, Archivo/JetBrains Mono type roles, and non-negotiables (one primary per view, accent = selection only, streaming beats batching) are compatible with Drape's editorial monochrome taste and strictly better engineered than what exists. Fit issues are enumerated in §B and all resolvable.

**Does Casting V2 fit the current backend?** Yes, with one genuinely new domain. The R7 authorities that V2 needs — durable operations (`generation_operations` + `operationContract.ts`/`operationRecovery.ts`), atomic idempotent credits (`atomicCredits.ts` + `uq_point_txn_user_ref`), immutable snapshots (`snapshotTransitions.ts`, `effectiveCastRead.ts`), private evidence (`privateEvidenceStorage.ts`, `evidenceDelivery.ts`), permanent deletion + storage cleanup (`finalCastDeletion.ts`, `storageCleanupWorker.ts`), whole-Cast restore, and explicit read projections (`modelReadProjections.ts`) — all survived the revert and are test-covered. What does **not** exist yet: a roll/candidate domain, a provider-neutral adapter layer (Gemini is called directly), a cohort-aware brief compiler, and an identity-retention gate that works for non-Gemini providers. Those are the new build, and they sit cleanly on top of the preserved authorities.

**Is the fresh-frontend / preserved-authority rebuild boundary correct?** Yes, emphatically. The evidence splits exactly along that line: the server side closed R7 with 3,182 passing tests and its laws (D-43 identity immutability, D-53 slot ledger, D-64 permanent deletion, D-65 evidence snapshots, D-70/71 visibility and probe laws) are the product's trust spine; the client side is where the founder's UX complaints live and where complexity has accumulated beyond repair-by-renovation (BoardPage.tsx 2,473 lines; CastingTakeover 758 lines with a 9-branch leave-confirm; cross-feature choreography via window events). Renovating the cockpit would preserve its information architecture, which is the actual problem.

**What should begin immediately:**
1. **Key rotation** (both pasted provider keys), then provider adapter **calibration spike** (M3): prove with real dev keys that GPT Image 2 gives eight good, diverse, consistently-framed candidates and that Nano Banana Pro actually holds a signed face across canonical views at Drape's quality bar. This is the highest-uncertainty item in the whole program and it gates everything downstream.
2. **Shared foundation** (M1–M2): tokens + AppShell + theme system behind new V2 routes. Platform work with zero product risk, needed by every later milestone.
3. **Roll domain design ratification** (this document §E–G) and its schema migration slice.

**What should stop immediately:**
1. Any work on the reverted tattoo/pose-projection subsystem, including "finishing" the R7-7G product gate as the planning brief's Phase A demanded — superseded (see §B conflict 1 and §N).
2. Any polish, extension, or new controls on the existing cockpit (ControlPanel, PackageHealthDialog, MasterPromptPanel, ViewTabs, the ink client workflow). Freeze except for safety fixes.
3. Lobby redesign work beyond wrapping it in the new shell — the Drape Studio prototype (future lobby) depends on vocabulary Casting V2 will establish (§D.15).

## F. Durable state machines

Server-owned; every transition happens inside a statement scoped to the authenticated owner. Client state is a projection, never authority. Invalid transitions return typed refusals and change nothing.

**Roll** — `pending → generating → {complete | partial | failed | cancelled}`; terminal states immutable (rolls are versions, never edited).
- `pending`: row + candidates created, credits charged (deduct-then-refund, reference = `operationChargeReference(opId)` bound at the running transition — the only idempotent charge mechanism the ledger honors), operation claimed. Crash at any point → a **bespoke roll adjudicator** in the recovery sweep (the `recoverEvidencePackageSyncOperation` precedent): it reads `casting_candidates` as durable truth (landed = has imageKey), fails still-dispatched candidates whose provider outcome is unqueryable, issues per-candidate slice refunds, finalizes `partial|failed`. **Recovery adjudicates and refunds; it never re-drives provider work** (existing sweep law). Never charges twice (claim replay by `(userId, clientRequestId)`).
- `generating`: candidate jobs dispatched under the concurrency budget.
- `complete`: all 8 terminal-ready. `partial`: ≥1 ready, ≥1 failed after retries (auto-refund for failed slots recorded on the operation). `failed`: 0 ready → full refund. `cancelled`: user cancelled; undispatched candidates refunded, in-flight ones run to completion server-side but are marked `expired` on landing (no cancel API on the creative engine — §H.9).
- Invalid: any transition out of a terminal state; any candidate mutation on a roll the user doesn't own; a second roll dispatch for the same operation key (replay returns the existing roll — idempotency, not error).

**Candidate** — full status enum: `queued | dispatched | ready | failed | discarded | signed | cancelled | expired`. Flow: `queued → dispatched → {ready | failed}`; `queued → cancelled` (roll-cancel CAS); `dispatched → expired` (landing after roll cancel); user-facing `ready → {kept ⇄ unkept} | discarded | signed`; lifecycle `→ expired → purged`.
- `failed` after N attempts (N=2 retries for retryable classes only) → refund slice; tile shows honest failure, never a stuck shimmer.
- `discarded`: pure delete from the visible roll; **also clears kept** (a card cannot be both); one-step undo restores exactly this candidate (`discarded → ready`, kept state NOT restored — dogfood note for M5: undoing a discard of a previously-kept candidate returns it unkept; founder confirms the feel). Discard is deduplicated (double-click idempotent). Undo stack clears on next roll dispatch.
- `signed`: only via the Sign ceremony; the sole transition that creates Cast authority.
- `expired`: retention window passed without keep/sign → cleanup eligible. The signed candidate and its kept siblings are exempt from expiry (retained while the Cast lives, §G.6).
- Invalid: keep/discard/follow on `queued|dispatched|failed|expired`; sign on anything but `ready`; any transition keyed by grid position (position is display metadata only); discard teaching the next roll anything (no write path exists from discard to compilation — enforced by design, tested).

**Generation progress** — per candidate: `queued → dispatched → ready|failed` projected to the client by polling the roll projection (2.5s cadence reusing the operation-bridge pattern). No provider names, no prompts in the projection. Skeleton tiles render immediately on roll creation; each swap happens on its own candidate's terminal event (streaming beats batching; never gated on the slowest).

**Keep** — desired-state CAS, not a toggle: the mutation carries `kept: true|false` and executes `… SET keptAt = ? WHERE … AND keptAt IS [NOT] NULL` (two-tab safe; the repo's CAS idiom, never read-modify-write). Keyed by candidate ID. Kept candidates appear (a) ringed on their own roll's grid, (b) in the cross-roll tray. On a *later* roll they appear in the tray only. Keep never charges, never generates.

**Discard / Undo** — above. Undo is **id-keyed**, not a server-popped stack: the client sends the candidatePublicId to restore, and the CAS is `status='discarded' → 'ready'` anchored `AND rollId = session.activeRollId` — which is also what enforces "undo clears on next roll" server-side (a stale tab cannot undo a discard from an earlier roll).

**Follow** — on a `ready|kept` candidate: creates a **new roll** (`parentCandidateId` lineage), same compiled brief + follow conditioning, fresh 8. Never mutates the source roll. The sheet header shows `FOLLOWING <index>` with a dismissible chip; dismissing only affects *future* rolls (existing rolls immutable).

**Shortlist (tray)** — the set of kept candidates across a session's rolls, ordered by keptAt. Signing removes nothing from the tray except the signed candidate (which becomes the Cast). The tray of an **open** session is the resumable “Unsigned sheet”; sessions are never “closed” by navigation (durable by design) — they only expire after 7 idle days (§G.6).

**Sign** — **one operation** (`castingV2.sign`) covering promotion *and* the canonical package — exactly the shape `casting.mint` uses today, so per-view refund slices reconcile against the same operation's charge (splitting Sign-charge from package-work would violate the receipt's credit-conservation assertion; verified against the finalize paths).
- Canonical sequence (compensation, not rollback — the credit authority runs its own transaction, and the storage copy is a network call): claim (no modelId yet → no lock; the candidate CAS below is the defense) → running (binds `op:<id>:charge`) → deduct Sign price → copy candidate image to Cast storage → **single DB transaction**: create `models` row (status **`provisioning`** — the existing "invisible, under construction" status, unreachable by every legacy procedure since they all require available statuses), identity snapshot + anchor, KI public id, lineage, and the **candidate CAS**: `UPDATE casting_candidates SET status='signed', signedCastId=? WHERE id=? AND userId=? AND status IN ('ready') AND signedCastId IS NULL` with `affectedRows===1` asserted inside the transaction (loser's model insert rolls back with it) → package views generate/validate/commit under this same operation with per-view integer refund slices → finalize; model transitions `provisioning → active` (minted) at package terminal, even if partial, and `bindGenerationOperationModel` runs **at activation, not before** (the bind helper and the standard snapshot spine are fenced on available statuses, which `provisioning` deliberately is not). **Mechanism ruling:** while the model is `provisioning`, signService and the package orchestrator use operation-scoped provisioning-aware writers — direct snapshot/slot inserts inside the Sign operation's transactions, following the `evidenceFork.ts` precedent (the only in-repo provisioning workflow, which works exactly this way) — then switch to the standard fenced `snapshotTransitions` writers from activation onward. The sign adjudicator locates the model via `casting_candidates.signedCastId`, never via the operation's (still-unbound) modelId.
- On failure before the durable boundary: `recordRefund` under the derived `refund:` reference, finalize failure, candidate remains `ready`. Stale mid-package crash → bespoke sign adjudicator (same pattern as the roll adjudicator): committed views stand, uncommitted slices refund, model still transitions to `active` with its completed slots (Cast usable from master — the progressive-package law).
- Exactly one candidate per ceremony (§B-13). The room opens immediately on the signed master (owner-scoped V2 projection reads `provisioning` casts); views stream in as they validate. Legacy library surfaces don't list `provisioning` rows — correctly, since they'd show a half-built package.
- Invalid: Sign on a foreign candidate (ownership in the CAS); double-Sign of the same candidate (the CAS; `UNIQUE(signedCastId)` remains as backstop only — it prevents two candidates claiming one Cast, not two Signs of one candidate); Sign racing discard (same CAS — a discarded candidate fails the status predicate).

**Package completion** — per view: `pending → generating → validating → {committed | failed(retrying) | failed(refunded)}`. Views commit individually (append-only slot ledger, D-53); the Cast is usable from the master alone; a failed view never blocks the others. All views included in the Sign price; per-view refund slices after retries exhaust. No user-facing per-slot purchasing.

**Identity revision** (post-V2.0 milestone, M12) — `draft request → classified (take|revision|fork) → priced → approved → frozen snapshot → affected views derived → generate+validate all affected → atomic commit | full rollback`. All-or-nothing: a half-updated package never becomes canonical truth (preserves the R7-7E law with the new engine underneath). Refusal or drift → previous coherent package stays current, honest refund.

**Canonical synchronization** — subsumed by the above: visibility derivation decides the affected set (reusing the generic `inkViewImpact` law: unknown impact fails closed to all-affected); unaffected views are reused, never regenerated.

**Take** — `requested → priced/confirmed → generating → validating identity → {landed | rejected}`. A Take records the identity snapshot it derived from; it never writes package or slot rows; rejection (identity drift) refunds and reports honestly. Historical Takes are immutable after landing (revisions never rewrite them).

**Retry** — automatic for `transport|rate_limit|timeout` classes with backoff, capped; never for `content_policy|capability` (those refund and surface honestly). Retries reuse the original operation budget — a retry can never charge again or duplicate a stored image (attempt-scoped storage keys; the landing step is idempotent per candidate).

**Refund** — always a recorded compensation on the operation (existing atomicCredits reference semantics), automatic at terminal failure, visible in the client as plain state ("2 didn't arrive — refunded"), never a support ticket.

**Cancellation** — roll-level, race-fenced by candidate CAS: cancel executes `UPDATE … SET status='cancelled' WHERE rollId=? AND userId=? AND status='queued'` and refunds **only the rows that CAS won** (per-candidate refund references keep retries idempotent); dispatch does a `queued→dispatched` CAS; landing does `dispatched→ready|expired` reading the roll's terminal status in the same statement. A candidate can therefore never be both refunded and delivered-*to-the-user*. **Late-landing generosity (founder ruling, 2026-07-31, post-M4):** a candidate that was already dispatched at cancel and lands `expired` — generated but never shown — **refunds its slice too** (distinct generosity refund reference; COGS recorded as absorbed via the provider telemetry, never billed). The product promise: *cancel refunds everything you haven't seen.* No abuse vector exists since expired candidates are never delivered. **Implemented in M5 (2026-07-31)** at the landing site in `rollService`, where the code knows the candidate landed unseen; the recovery sweep deliberately does not repeat it, because `expired` is also written by the 7-day retention sweep over work the user did receive, and refunding on the status alone would undo the sweep correction (44748ae5). One consequence is stated rather than hidden: a crash between the landing CAS and the refund leaves that slice unrefunded, the same window the failure-refund path has always had — closing it needs a status that separates the two meanings of `expired`, which is a migration no milestone has yet needed. Sign package and revisions: not user-cancellable mid-flight (atomicity), but recoverable/refundable on failure. Session close/navigation cancels nothing (durable operations continue; the sheet resumes from server truth — same law as the existing operation bridge).

**Cleanup** — `expired|discarded-past-undo|failed` candidates → storage-cleanup batches (existing worker) delete R2 objects + rows after the retention windows in §G.6. Cleanup never touches signed candidates, kept siblings of a signed candidate, or any Cast-owned object; kept-but-unsigned candidates purge with their session at expiry (§G.6). Deletion of a Cast (D-64, permanent) additionally purges its roll lineage per §G.6.

## H. Billing and provider contracts

**H.1 When price is displayed.** On every paid affordance before it fires (D-15): "Cast it · N cr" on the roster CTA and TRY chips' dock, "Roll again · N cr" persistently on the sheet dock (nudge chips inherit it), Sign confirm shows the full Sign price with what it includes ("locks the face, builds the complete view package"), Take/revision ceremonies quote before approval. Credit balance visible in the topbar on all casting surfaces (D-45).

**H.2 Reserve/deduct.** Deduct after the operation's running transition, **always with `referenceId = operationChargeReference(operationId)`** — the bare `withAtomicCredits` fallback mints a fresh reference per invocation and would double-charge on crash-retry, so V2 executors must pin the reference explicitly (this is the mechanism, not a convention). Compensate by automatic refund slices via the shared derivation helpers. No shadow "reservations" system.

**H.3 Roll pricing.** One price per roll of 8, defined as **8 × an integer per-candidate price** (the ledger is integer-only and refund slices are read from each candidate's persisted `pointsCost` — never derived as a fraction). Follow-rolls and nudge-rolls cost the same as plain rolls (same work). Partial failure: automatic per-candidate slice refunds.

**H.4 Sign pricing.** One price, one operation (`castingV2.sign`, §F): face lock, likeness anchor, and the **entire canonical view package** for the Cast's cohort profile, with the price internally decomposed into a promotion portion + integer per-view portions so failed views refund their exact slice under the same operation's charge reference (the mintPackage `<chargeRef>:slot:<angle>` pattern). No per-slot purchasing exists anywhere in V2 (supersedes the tiered mint UX; D-72's progressive-package law survives internally as "Cast usable from master while views stream").

**H.5 Retry laws.** Auto-retry retryable classes only, ≤2 retries, exponential backoff, within the original charge. Manual "try again" on a failed candidate slot (post-refund) is a new priced micro-operation only if offered; V2.0 instead offers Roll again (simpler, already priced).

**H.6 Cancellation laws.** §F. Refund anything never dispatched; never refund delivered work; ambiguous provider outcomes (timeout after dispatch) resolve via the recovery worker: verify terminal provider state where queryable (Fal status API), else fail the attempt, refund the slice, and record the ambiguity on the operation.

**H.7 No-double-charge.** Operation key uniqueness at the credit ledger (exists, tested); roll replay by key returns the same roll; Sign is idempotent per candidate; package/revision commits idempotent per operation.

**H.8 Queue admission & rate limits.** A per-provider concurrency budget (env: `ROLL_IMAGE_CONCURRENCY`, default 8) and a global queue-depth cap (pattern exists as `GEMINI_MAX_QUEUE_DEPTH`); when depth would exceed the cap, roll creation refuses honestly ("Studio is busy") with a real `TOO_MANY_REQUESTS` — never a silent queue of unbounded spend. Provider 429s are retryable-with-backoff and consume no extra budget. Circuit-breaker pattern (exists for Gemini) generalizes per provider adapter.

## I. Character/cohort model

**Subject/body profile** (`human | humanlike` [android/orc/elf — bipedal, face-bearing] `| anthro | creature`) and **visual style** (`photoreal | anime | illustrated | cel | 3d | painterly`) are independent columns of a compiled brief, inferred by the brief compiler, correctable as chips, and stored on the Cast at Sign.

**Cohort** = resolved (profile, style) pair mapped to a **cohort adapter** — a server-owned policy object (registry pattern, like the existing anatomy registry's tuple→policy shape):
- `compilePrompt(brief, locks)` — cohort-appropriate compiled instruction; the current photoreal-human prompt architecture becomes exactly one adapter, not universal law.
- `sheetFraming()` — the normalized casting treatment (neutral wardrobe, consistent crop/light per style) so candidates compare as characters, not as art directions.
- `viewPackageProfile()` — canonical slots for this cohort (humanlike cohorts share the portrait/front/side/three-quarter/back/motion family; non-standard bodies may define different packages later without schema change — slots are rows, not columns).
- `identityValidationPolicy()` — how "same character" is judged: photoreal humans → multimodal-judge + anchor comparison; anime/illustrated → structural traits (eye shape, hair silhouette, palette, linework) via multimodal judge with cohort-specific rubric; **fail closed** where no trustworthy verifier exists (the request refuses before spend, not after).
- `capabilities()` — honest downstream truth per Cast: `{multiview, revision, takes, voice, wardrobeVto, canvas, video, export…}` each `full | calibrated | unsupported`. Wardrobe/VTO: full for photoreal humans, calibrated for stylized humans, unsupported initially beyond that — a non-human Cast is never rejected at casting because VTO can't dress it; the capability projection just says so.

**Certified cohorts at launch:** photoreal humans; anime/stylized humans; humanlike fantasy/androids. Uncertified combinations refuse at compile time with honest copy ("can't cast non-humanoid creatures yet") — before any spend. The registry admits later cohorts by adding adapters + calibration, not by schema or product rewrite.

**Wardrobe-baseline law (founder ruling, 2026-07-30):** the legacy rule forcing casts into undergarments/minimal clothing was a VTO plumbing need masquerading as casting law — it is retired as presentation. In V2: **presentation views are clothed** (per-cohort neutral wardrobe — grey-tee-class for humans, cohort-appropriate neutral for others); the minimal-clothing **VTO base becomes an internal package slot** for wardrobe-capable cohorts only (photoreal humans initially), generated with the package or on first wardrobe use, consumed by VTO, never shown in roster/room as the hero. Non-VTO cohorts get no such slot (capability truth). For stylized cohorts where an outfit is character-defining (mascot suits, signature costumes), the outfit is an identity/style fact that locks at Sign. Per-cohort neutral-wardrobe definitions live in the cohort adapter's sheetFraming.

**Creative-direction mixer (founder note, 2026-07-30):** a named part of what made legacy photoreal output excellent is the vibe/brand mixer — the editorial/commercial/runway blend, `BRAND_PROFILES` expressions, and blend-driven studio settings in `geminiPrompts.ts`. It ports into the photoreal cohort adapter as the creative-direction compilation layer (explicitly on the M4/M5 mining list, not deletable form plumbing): inputs arrive sentence-first (interpreter infers the blend, surfaced as a chip), the tri-blend control survives in the Advanced "Creative direction" group for power users, stated energy locks across the sheet while unstated energy is a prime treatment-variation axis. Boundary: the mixer shapes energy/expression/presence only — props, wardrobe and framing remain with the adapter's framing law.

**Craft-reference law (founder ruling, 2026-07-30, clarified same day):** `docs/specs/CASTING_V2_LEGACY_CRAFT_CATALOG.md` is the exhaustive inventory (~100 mechanisms) of legacy engineered craft — **reference, not requirements.** The legacy system was deliberately strict and stringent; V2 does not inherit that rigidity, and the planning brief's own critique (over-literal checklists reduce creative latitude) stands. The obligation is only this: compiler-touching milestones **consult** the catalog (M4/M5 photorealism/direction/vocabularies incl. the weighted randomizer → Surprise me; interpreter design ← the parser's restraint doctrine H7–H16; M7 ← per-angle framing directives; M12 ← edit-protocol language) so that nothing valuable is lost *by accident* — adoption of any item is a per-item judgment against V2's own laws (creative freedom by default, framing discipline, founder-graded quality bar). The quality standard is the founder's side-by-side grade of the *output*, never compliance with legacy protocol text.

**Heritage/ethnicity blend (founder ruling, 2026-07-30):** the legacy ethnicity-blend system (structured components + dominance bands, the engineered hint language, and the phenotype lock) works extremely well and **carries into V2 as named ported craft**: heritage is a structured identity fact extracted sentence-first by the interpreter (stated → locked across the sheet, chip-visible; deliberate blend composition survives in the Advanced Identity group); the dominance-band and phenotype-lock language ports into the photoreal adapter's compiler alongside the skin protocols and mixer; **unstated heritage is a prime treatment-variation axis** (real casting diversity when nothing was locked); post-Sign it locks in the identity snapshot and the multi-subject identity gate (pre-M7 condition) verifies retention holds across demographics, not just one.

**Archetype library (founder ruling, 2026-07-30):** the legacy blend library is high-fashion-only and cannot cover V2's open front door. Generalization: curated profiles become **archetype anchors** (fashion houses joined by K-pop idol, UGC creator, athlete, corporate, streetwear, …), each authored at the same craft level; the interpreter picks/blends from the shelf via the existing mixer math. For briefs no anchor fits, the interpreter **composes** a direction profile in the same structured format and vocabulary grammar as curated entries — never raw freeform prompt text — with the framing law still owning everything physical. Composed profiles are logged; recurring archetypes graduate into the curated shelf. Real brand names remain internal-only vocabulary (never in any projection) and should migrate to descriptive names ("quiet luxury") when the adapter is built. Archetype shelves are per-cohort over time (anime has its own archetypes).

**Style-profile law (founder ruling, 2026-07-30):** a coarse `styleKey` routes to the cohort adapter, but stylized cohorts additionally carry a compiled **style profile** — the specific sub-style descriptors ("90s cel, thick linework, muted palette") inferred from the brief, internal state surfaced as a removable chip. It obeys the existing Locked/Varying law: stated → locked constant across the sheet; unstated → creative latitude (candidates may vary sub-style moderately, each internally consistent), and **the signed candidate's realized style locks at Sign** as part of the identity snapshot. Every downstream view/Take/revision compiles under the locked profile, and the cohort validator checks style integrity (linework, palette, rendering treatment vs. the anchor) — for a stylized cast, art style *is* identity. Applies equally to illustrated/painterly cohorts. Schema note: `styleProfile` json (internal) alongside `styleKey` on rolls and Casts — additive.

**Cohort quality law (founder ruling, 2026-07-30, post-M3):** each cohort adapter is a *quality-engineered prompt system* of the same caliber as the legacy Gemini photoreal engineering — authored and tuned per cohort (anime has its own high-fidelity engineering; a photoreal orc gets the realism engineering with adapted anatomy, not a generic fantasy prompt). The fidelity/discipline layer (studio spec, pose/expression range, wardrobe neutrality, anti-CGI/style-integrity constraints) is a **code-owned cohort constant** that interpreter and treatment output can never touch — variety lives in *who* the character is, never in how they are photographed. "Certified" at M9 means exactly this: the cohort's sheets meet the legacy system's quality bar in a founder-graded side-by-side; a cohort that merely functions is not certified. (Evidence basis: M3 calibration showed a minimal framing fixture leaks props/costume — see the M5 precedence conditions.)

**Identity-retention policy** is cohort law, not prompt law: every identity-preserving generation (view, Take, revision) passes the cohort's validator against the signed anchor before landing; prompt compliance is never the sole check (settled anti-pattern).

**Unsupported-combination behavior:** refuse pre-spend at brief compile; if a *supported* cast later requests an unsupported downstream op, the projection has already told the client to render it unavailable — and the server refuses anyway (a control not on the request path doesn't exist).

## E. Casting V2 domain architecture

New server domain `server/castingV2/` (facade over preserved authorities; no old screen-choreography reuse) + new tRPC namespace `castingV2.*` (additive — legacy routers untouched until the M14 retirement milestone). New client feature `client/src/features/casting-v2/` on foundation primitives, with a deliberately small ephemeral store (hover, dialog, undo-toast — all durable truth lives server-side).

Boundaries (each a module with its own tests):

- **Brief compiler** (`server/castingV2/briefCompiler.ts`) — sentence (+ chips/locks) → **CastingIntent**: {subjectProfile, visualStyle, cohortKey, locked facts, explicitly-varying dimensions, open-to-creativity dimensions, persona line}. **Interpreter model: Claude** (via OpenRouter; default candidate `anthropic/claude-sonnet-5`, confirmed and pinned in the M3 report, and the pinned id recorded per roll — founder proposal, adopted; assessment in §E.1). The LLM's output is never authority: it must parse into a strict zod schema, lock extraction is re-validated deterministically, and interpreter failure is an honest free refusal, never a guess. Explicit facts → locked; omissions → varying (settled law). Emits the chip list for the projection.

**E.1 Brief-interpretation pipeline (founder proposal 2026-07-30, assessed — not blindly accepted).** Proposed flow: sentence → Claude CastingIntent → *(optional)* Kimi K3 proposes eight constrained creative treatments → deterministic provider adapter builds engine requests → GPT Image 2 candidates → NBP for signed-identity work.
  - **Claude as semantic interpreter: adopt now.** The compiler was already an LLM stage; Claude is the best instruction-follower for structured extraction, the OpenRouter transport already exists in this design, and per-parse cost is negligible. Deterministic validation downstream is unchanged — the interpreter proposes, code disposes.
  - **Deterministic adapter owns all technical request detail: adopt now** (this was already law in §E — model ids, dimensions, framing blocks, reference attachments, provider params are code, never LLM output).
  - **Kimi K3 as constrained creative director: plausible, unproven — gated by an A/B at M3, optional and fail-safe by construction.** Value hypothesis: eight identical prompts rely on sampling temperature for diversity and can produce near-duplicates; eight *authored* treatments give controlled, labeled diversity (bonus: each candidate's personaLine — "Warm, unhurried", "Dry and flat" — derives from its treatment instead of being invented after the fact). Risks and mitigations: (a) *lock violations* — every treatment is deterministically validated against the CastingIntent's locked facts; a violating treatment is dropped, and if fewer than 8 survive the roll falls back to Path A entirely; (b) *comparability* — the settled near-constant-framing ruling is a **rule, not an experiment**: the deterministic adapter's normalized block owns framing, camera, crop, **and neutral wardrobe/scene** (matching §I's sheetFraming exactly). Kimi varies character-side dimensions only (personality, energy, unlocked hair/styling). The M3 A/B may *propose* relaxing wardrobe/scene variance, but shipping that requires an explicit founder-approved amendment to §I — evidence can argue for a rule change; only a ruling makes one; (c) *latency* — one extra text call (est. 2–5s) before dispatch; skeletons render at roll creation so perceived cost is small; a 5s timeout falls back to Path A; (d) *dependency risk* — the stage is a config (`ROLL_TREATMENT_STAGE=off|kimi`), fails safely to Path A per roll, stores treatments as internal provenance json, and touches no schema.
  - **A/B gate (in the M3 harness):** 12-brief matrix (tight, loose, and non-human briefs × 4), both paths — **A:** Claude intent → adapter → GPT Image 2; **B:** Claude intent → Kimi treatments → adapter → GPT Image 2. Scored on: locked-fact fidelity (validator + founder), meaningful diversity, visual quality, duplicate rate, added latency, refusal rate, cost per roll. Decision rule: **B ships only if it beats A on diversity/duplication without losing fidelity or quality and within +5s median** — otherwise V2 launches on Path A with the stage flag kept for later re-evaluation. Kimi K3's OpenRouter availability/pricing is itself an M3 verification item (the stage is model-agnostic; if K3 isn't servable, the same A/B can run with another inexpensive creative LLM).

## G. Data model and migrations

New tables (Drizzle, MySQL), additive-only slices. Existing `models`, snapshot, slot-ledger, operation, credit, and cleanup tables are reused *at Sign and after* — their semantics genuinely match there and only there. Candidate/evidence tables are **not** reused for rolls (semantics differ: evidence is owned identity truth; candidates are exploratory, expiring, non-authoritative — the planning brief's warning is honored).

*(Convention note: all "→" references below are **logical FKs** — indexed plain columns + application joins, matching the repo's schema, which contains zero engine-level foreign keys; engine FKs would fight `db:push`, D-64 purge ordering, and the append-only journal.)*

**`casting_sessions`** — the resumable unsigned sheet.
`id` PK · `publicId` (opaque, unique) · `userId` →users (ownership predicate on every statement) · `originType` enum(`roster|canvas|wardrobe`) · `originBoardId`/`originItemId` nullable (server-owned canvas return destination; **verified against board ownership at session create**, in the same statement) · `activeRollId` nullable · `status` enum(`open|abandoned|expired`) — a session **stays `open` after a Sign** (multiple Signs per session are legal, each its own ceremony; the tray keeps the rest) with `signedCastCount` incremented · `parentCastId` nullable (fork-from-room lineage; **resolved through `models.userId` + availability in the same statement**) · `createdAt` · `lastActivityAt` · `expiresAt`.
Indexes: (userId, status), expiresAt. `rollIndex` allocation and `activeRollId` updates serialize under `SELECT … FOR UPDATE` on this row, so two tabs rolling concurrently get sequential indexes instead of a duplicate-key failure after the charge.

**`casting_rolls`**
`id` PK · `publicId` unique · `sessionId` →casting_sessions · `userId` (denormalized for single-statement ownership) · `rollIndex` int (per session; unique(sessionId, rollIndex); allocated under the session row lock) · `briefText` text (user's sentence) · `compiledBrief` json **internal** · `cohortKey` · `styleKey` · `lockContract` json · `parentRollId` / `parentCandidateId` nullable (follow lineage; **the parent candidate is resolved through `casting_candidates.userId = ctx.user.id` in the same insert-select** — a client-supplied lineage id can never reference a foreign candidate) · `status` enum(§F) · `priceCredits` int (= 8 × perCandidateCredits, integer by construction) · `operationId` →generation_operations (idempotency + recovery + refund authority; kind `castingV2.roll`) · `createdAt`.
Unique: operationId. Index: (sessionId, rollIndex).

**`casting_candidates`**
`id` PK · `publicId` unique · `rollId` →casting_rolls · `sessionId` (denormalized — the tray query is session-scoped) · `userId` (denormalized) · `position` tinyint (display only; unique(rollId, position)) · `status` enum(§F; all transitions are CAS predicates) · `pointsCost` int (the integer per-candidate slice; refund authority reads it from the row, never derives a fraction) · `imageKey` / `thumbKey` nullable (R2 keys; UUID-based) · `provider` / `providerModel` / `providerRef` (**internal** provenance, D-12) · `personaLine` varchar · `internalPrompt` json **internal** · `keptAt` nullable · `discardedAt` nullable · `attemptCount` tinyint · `failureClass` nullable · `signedCastId` nullable →models (set only by the Sign CAS; `UNIQUE(signedCastId)` as backstop — the CAS is the double-Sign defense, §F) · `createdAt` · `expiresAt`.
Indexes: (rollId), (sessionId, keptAt) for the tray, expiresAt for cleanup.
Per-candidate attempts additionally write **one `generations` row per candidate slot** with stepKey `variation:<n>` (reusing the existing refund-reference branch and the existing `castingImage` type — no `generations.type` enum ALTER), **mutated in place across retries** via `updateGeneration` exactly as `mintPackage` does — never one row per attempt, which would double-refund a slot that failed once then succeeded.

**`casting_takes`** (M8)
`id` PK · `publicId` unique · `castId` →models · `userId` · `kind` enum(`image|video`) · `label` varchar · `imageKey`/`url` · `identitySnapshotId` (the snapshot it derived from — provenance, never rewritten) · `operationId` (kind `castingV2.take`) · `status` · `createdAt`.

**Cast additions** (additive columns on `models` at M7): `cohortKey`, `styleKey`, `sourceCandidateId` nullable, `sourceRollId` nullable. **No new status enum value**: the Sign→package window uses the existing `provisioning` status (§F Sign), which every legacy procedure already treats as unavailable; package terminal transitions it to `active`/minted.

**Operation kinds:** `castingV2.roll`, `castingV2.sign` (promotion + package, one op), `castingV2.take`, and `castingV2.revision` at M12 — dot-namespaced per the contract's convention (`kind` is varchar(48), no migration needed to write new kinds). Each new kind ships with: its entry in the recovery sweep's exhaustive kind Records, a bespoke adjudicator (roll, sign) or the generic path (take), and its refund-reference derivation through the shared helpers (`refundReferenceFor`/`childRefundReference` — never string concatenation at two sites; references >64 chars are transparently hashed, so writer and recovery must use the same helper).

**Rollback-skew hardening (must ship before any V2 kind is written in production):** `listActivePublicGenerationOperations`/`getRecentPublicGenerationOperation` currently map **every** row through a projection that hard-throws on unknown kinds — after a rollback, one in-flight V2 receipt would 500 the legacy operation bridge for that user until the row settles. A standalone slice makes those readers filter to known kinds (skip-and-log unknowns) ahead of M4.

**Ownership predicates.** Every read/write: `WHERE userId = ctx.user.id` in the same statement (denormalized userId on rolls/candidates exists precisely so child mutations need no two-step check); child ids re-anchored via joins (`UPDATE casting_candidates c JOIN casting_rolls r ON c.rollId=r.id AND r.userId=? SET … WHERE c.id=? AND c.userId=?`). Bulk ops (multi-discard) refuse atomically on any foreign/missing/duplicate id.

**G.6 Expiry/cleanup fields & policy — DECIDED (founder, 2026-07-30): nothing unused outlives its sheet.** The founder's ruling is aggressive cleanup; the only survivors are deliberate choices. Two settled product features bound how aggressive mid-session cleanup can be: roll history ("go back to roll 01") and the Siblings card both need candidates to exist while their session/Cast does. The reconciled policy:
- **there is no user-facing "close"** — navigation never destroys work (durable-by-design law); a session's only states are `open → expired`;
- **while a session is open:** all its rolls and candidates remain (roll history + tray are settled features); discarded candidates purge once no longer undoable (next roll), min 24h; Sign refreshes `lastActivityAt` and leaves the session open (multiple Signs legal);
- **sessions expire after 7 idle days** (the resumable "Unsigned sheet" window — short by ruling): at expiry everything purges — rolls, candidates, objects — **except** signed candidates (their rows persist as Cast lineage) and kept siblings of a signed candidate (retained while that Cast lives, for the Siblings card);
- Cast deletion (D-64): purges its source roll lineage in the same ceremony.
All object deletion flows through the existing `storage_cleanup_batches`/`_items` worker. Two mechanics the review pinned down: retention sweeps are not user operations, so each cleanup batch mints a synthetic UUID for the batch's `operationId` (NOT NULL + unique + UUID-validated); and the batch `kind` enum gains the value **`casting_candidate_cleanup`** (`candidate_cleanup` is already taken — it means *evidence* candidates). This enum ALTER is declared in slice 0017 and must update the two contract points that pin the enum DDL: the hardcoded enum string in `server/casting/evidence/evidenceComposerSchema.ts` and `server/r7-evidence-ingestion-contract.test.ts`. Thumb-downgrade-after-90-days is **cut from V2.0** (the cleanup worker deletes exact keys; it has no transform capability — that would be a new worker for marginal storage savings).

**Versioning & lineage.** Rolls are immutable versions (no UPDATE after terminal except retention flags); lineage is FK-explicit (roll→roll, roll→candidate, cast→candidate/roll, session→cast for forks). History is readable as states (D-73 pattern).

**Migration slices** (each independently deployable, forward-only per the append-only journal discipline):
1. `0017_casting_v2_sessions_rolls_candidates` — three new tables + one additive enum value on `storage_cleanup_batches.kind` (the only existing-table touch). Ships with M4, after the rollback-skew hardening slice above.
2. `0018_casting_v2_sign_lineage` — `models` additive columns, **plus the late-landing refund idempotency column on `casting_candidates`** (founder instruction, 2026-07-31: scheduled debt, not a floating caveat). Ships with M7.

   The debt it settles: `expired` currently means two different things — a candidate that landed unseen after a cancel (refunded under the generosity rule) and one the 7-day retention sweep aged out after the user looked at it for a week (never refunded). Because the status cannot tell them apart, the M5 refund happens inline at the landing site and the recovery sweep must keep its hands off, which leaves a crash between the landing CAS and the refund as an unrefunded slice. The column separates the two meanings so recovery can adjudicate `expired` safely: a nullable `unseenRefundedAt` (or an `expiredReason` enum — decide at implementation) written in the same statement as the landing CAS, making the generosity refund idempotent and durable rather than best-effort. Additive; old code ignores it.
3. `0019_casting_v2_takes` — takes table. Ships with M8.
4. `0019b_casting_v2_voices` — `cast_voices` table (`id` PK · `publicId` · `castId` →models · `userId` · `label` · `voiceDescription` (the user's design prompt) · `providerVoiceRef` **internal** · `sampleKey` (R2, audition clip) · `status` · `operationId` · `createdAt`; one active voice per cast via nullable `activeForCastId` + unique — the multi-NULL pattern). Ships with M8b.
5. `0020_casting_v2_revision_ops` — revision operation kind metadata if needed. Ships with M12.
Compatibility: no slice alters existing columns; old code ignores new tables; `pnpm db:push` per current discipline; disposable-DB tests per slice before any production migration.

## P. Drape Atlas — internal self-documenting architecture map (founder directive 2026-07-30; planning only, not implemented in this review)

Artifacts: `docs/architecture/drape-architecture.json` (canonical, machine-readable) · `drape-architecture.schema.json` (its validated schema) · `index.html` (filterable explorer, derived from the JSON, never the other way) · `scripts/generate-architecture.mts` (generator) · package commands `architecture:generate` / `architecture:check`.

**P.1 Smallest useful first version (M2b) — capped scope.** v1 maps only what Casting V2 implementation and legacy retirement consume, all mechanically derived:
- **Routes & auth:** every tRPC procedure (namespace, name, query/mutation, auth class from which builder declared it — public/protected/admin/moderator, whether its input schema calls `.strict()`, rate-limit call presence) and every Express route mounted in `server/_core/index.ts` with its auth treatment. Client-facing procedures without a classifiable auth builder are a **finding**, not a guess.
- **Product domains & modules:** file inventory under `server/` and `client/src/` with domain assignment (path-inferred; annotation override) and lifecycle status (`active | compat | retire | delete` — seeded directly from this plan's §C map).
- **Env vars (names only, never values), feature flags** (the scope-flag modules and their `off|all|users:` grammar), **workers/schedulers** (everything started from `_core/index.ts`), **operation kinds** (from `operationContract.ts`), **credit-cost constants**.
- **Findings (v1 set):** disconnected routes (mounted but unreachable or vice versa), dormant controls (exported guard/limit helpers with zero call sites on any request path — the "currently not enforced" class CLAUDE.md already documents by hand), unreferenced workers, unclassified client-facing procedures, and retire/delete-marked modules that still have live importers.
- **Views (v1):** domains · routes & access control · env/flags · workers · legacy retirement · disconnected-or-suspicious. Each a filtered projection of the JSON — never one flat diagram.

**P.2 Later extensions, each landing with the milestone that consumes it:** billing/charge/refund path mapping + receipt/idempotency coverage (with M4, when the V2 kinds exist); write-statement ↔ ownership-predicate mapping and DB read/write edges (with M4/M7 — this is static-analysis-hard; it starts as curated annotation over the db/ helpers and mechanizes opportunistically); client request paths (which surfaces call which procedures — scan of `trpc.*` usage; with M5); storage namespaces and read/write sites (with M7); provider operations map (with M3); state-machine catalog (from §F, with M4); behavioral/contract-test cross-references (with M13's absence tests); DB relationship view from the drizzle AST (any time, cheap).

**P.3 Mechanical extraction sources (exact):** ts-morph over the repo tsconfig for import graphs and call-site queries; `drizzle/schema.ts` AST for tables/columns/uniques/indexes; source AST of `server/routers.ts` + `server/routes/**` for procedure declarations and builder identity; `server/_core/index.ts` AST for Express mounts, middleware order, and worker starts; `server/_core/env.ts` + a `process.env` scan for env names; `package.json` for scripts; `client/src/App.tsx` for pages/routes; globs for stores (`use*Store`), tests (`*.test.ts`, `*.integration.test.ts`). Nothing executes app code except optionally importing the assembled `appRouter` type-level metadata; the generator never opens a DB connection, never reads `.env` values, never touches R2.

**P.4 Annotation format.** `docs/architecture/annotations.yaml` (schema-validated alongside the main schema): entries keyed by module path or route id, carrying only what code cannot say — domain overrides, lifecycle status + planned-removal milestone, one-line semantic purpose, and `acceptedFindings` (deliberate exceptions, e.g. a knowingly-dormant control, so the check stays green without silencing the class). The generator **fails** on annotations referencing nonexistent paths/routes — annotations can't rot silently. Everything else is mechanical; if an annotation restates something derivable, the generator warns.

**P.5 JSON schema design.** One document: `meta {schemaVersion, generatorVersion, sourceFingerprint}`, then entity arrays (`domains, modules, surfaces, routes, tables, envVars, flags, workers, providers, operationKinds, storageNamespaces, stateMachines, tests`), one `edges` array (`{from, to, kind: imports|calls|guards|reads|writes|charges|refunds|cleans}` over entity ids), and `findings` (`{id, severity, kind, subject, message, accepted?}`). Ids are stable, human-readable strings (`route:castingV2.roll.create`, `module:server/casting/atomicCredits.ts`). `drape-architecture.schema.json` is JSON Schema draft 2020-12, enforced by ajv inside both generate and check.

**P.6 Deterministic generation.** All arrays stable-sorted by id; no timestamps anywhere; `sourceFingerprint` is a hash over the *tracked source inputs'* contents (excluding `docs/architecture/**` itself) — reproducible for identical sources, and immune to the impossible commit/regenerate loop that embedding the current commit SHA would create (the current git HEAD is *reported* alongside as informational output of the check, never written into the file). Two consecutive generates on an unchanged tree must be byte-identical; that is itself a test.

**P.7 CI validation.** The repo has no CI service today, so the enforcement lands in two layers: (1) a vitest guard in the normal suite runs `architecture:check` logic (regenerate to temp → byte-diff against committed → schema-validate → diff the findings list against the committed one, so *newly* disconnected controls or unmapped authority boundaries fail loudly) — meaning `pnpm test`, which already gates every push per the collaboration rules, is the CI; (2) when/if GitHub Actions is added, the same check runs there and may publish `index.html` as an internal build artifact. **CI never commits regenerated files** — the developer or agent regenerates, inspects the diff, and includes it in the reviewed change like any other file.

**P.8 CLAUDE.md maintenance contract (text added at M2b implementation, verbatim):** *"Architecture Atlas: after changing routes, schemas, database access, ownership rules, billing, workers, queues, providers, storage, feature flags, product-domain boundaries or legacy-module status, run `pnpm architecture:generate` and review the diff as part of the change. Before completing work, run `pnpm architecture:check`. Generated architecture files are reviewed with the code change and never edited manually; annotations live in `docs/architecture/annotations.yaml`."*

**P.9 Internal HTML publication.** `index.html` is a single self-contained static file (inline JS/CSS, the JSON embedded at generation — no external requests, no server). It lives under `docs/`, outside `client/src`, so Vite never bundles it; a guard test asserts nothing under `dist/public` contains the Atlas payload. It holds no secrets by construction (P.3: the generator can't see values), and the check additionally greps the outputs against a deny-pattern list (env value shapes, key prefixes, R2 URLs with credentials) as a belt-and-braces test. Optional later: CI artifact upload for browsing per-branch.

**P.10 How Atlas failures gate work.** `architecture:check` failing is a red build exactly like a failing test — it blocks milestone completion and, because deploys are gated on the suite, deploys too. Three failure classes, three responses: *stale output* → regenerate and include the diff (cheap, deterministic); *schema-invalid or nondeterministic output* → generator bug, fix before proceeding; *new unaccepted finding* (a control went dormant, a write lost its ownership mapping, a retired module gained a caller) → either fix the code or record a reviewed `acceptedFindings` entry with justification — silence is never an option. The M14 retirement milestone uses the legacy-retirement and disconnected-code views as its authority: nothing is deleted while the Atlas shows live callers, and nothing marked deleted may reappear without tripping the findings diff.
